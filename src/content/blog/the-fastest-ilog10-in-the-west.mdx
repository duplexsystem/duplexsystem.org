But if you're curious how I got here, and when this is the fastest, read on:

## Back in 2021

Back in 2021 I was attempting to write a silly little C++ program, whose purpose I have since forgotten. As I often do when learning a new language, I imposed a set of restrictions on myself to develop my skills: this time I decided to try and use no branching, loops, recursion, or division.[^1]

At some point in the program I needed to count the (base 10) digits in a number. After some quick research I learned that this is the same as `ceil(log10(x + 1))`, or more simply expressed `ilog10(x) + 1`. Quick and easy, no loops or branching, I thought. However, curiosity got the better of me and I decided to take a look at glibc's implementation of these functions. Let's look at `ceil` first:

```c title="[s_ceil.c](https://sourceware.org/git/?p=glibc.git;a=blob;f=sysdeps/ieee754/dbl-64/s_ceil.c)" dir="sysdeps/ieee754/dbl-64" showLineNumbers footer="Copyright (C) 1993 Sun Microsystems, Inc. [SunPro license](/licenses/SunPro.txt)"
double
__ceil (double x)
{
#if USE_CEIL_BUILTIN
  return __builtin_ceil (x);
#else
  /* Use generic implementation.  */
  int64_t i0, i;
  int32_t j0;
  EXTRACT_WORDS64 (i0, x);
  j0 = ((i0 >> 52) & 0x7ff) - 0x3ff;
  if (j0 <= 51)
    {
      if (j0 < 0)
        {
          /* return 0 * sign(x) if |x| < 1  */
          if (i0 < 0)
            i0 = INT64_C (0x8000000000000000);
          else if (i0 != 0)
            i0 = INT64_C (0x3ff0000000000000);
        }
      else
        {
          i = INT64_C (0x000fffffffffffff) >> j0;
          if ((i0 & i) == 0)
            return x;                   /* x is integral  */
          if (i0 > 0)
            i0 += UINT64_C (0x0010000000000000) >> j0;
          i0 &= ~i;
        }
    }
  else
    {
      if (j0 == 0x400)
        return x + x;                   /* inf or NaN  */
      else
        return x;                       /* x is integral  */
    }
  INSERT_WORDS64 (x, i0);
  return x;
#endif /* ! USE_CEIL_BUILTIN  */
}
```

Ignoring the very likely possibility of a native implementation, this is not ideal if we're avoiding branching. However, in this instance I was not concerned with handling of special floating point cases, so instead of `ceil` we can use truncation when converting from `double` to `long`, by taking `log10(x) + 1` rather than `log10(x + 1)`. Now let's look at `log10`:

```c title="[e_log10.c](https://sourceware.org/git/?p=glibc.git;a=blob;f=sysdeps/ieee754/dbl-64/e_log10.c)" dir="sysdeps/ieee754/dbl-64" showLineNumbers footer="Copyright (C) 1993 Sun Microsystems, Inc. [SunPro license](/licenses/SunPro.txt)"
double
__ieee754_log10 (double x)
{
  double y, z;
  int64_t i, hx;
  int32_t k;

  EXTRACT_WORDS64 (hx, x);

  k = 0;
  if (hx < INT64_C(0x0010000000000000))
    {                           /* x < 2**-1022  */
      if (__glibc_unlikely ((hx & UINT64_C(0x7fffffffffffffff)) == 0))
        return -two54 / fabs (x);       /* log(+-0)=-inf  */
      if (__glibc_unlikely (hx < 0))
        return (x - x) / (x - x);       /* log(-#) = NaN  */
      k -= 54;
      x *= two54;               /* subnormal number, scale up x  */
      EXTRACT_WORDS64 (hx, x);
    }
  /* scale up resulted in a NaN number  */
  if (__glibc_unlikely (hx >= UINT64_C(0x7ff0000000000000)))
    return x + x;
  k += (hx >> 52) - 1023;
  i = ((uint64_t) k & UINT64_C(0x8000000000000000)) >> 63;
  hx = (hx & UINT64_C(0x000fffffffffffff)) | ((0x3ff - i) << 52);
  y = (double) (k + i);
  if (FIX_INT_FP_CONVERT_ZERO && y == 0.0)
    y = 0.0;
  INSERT_WORDS64 (x, hx);
  z = y * log10_2lo + ivln10 * __ieee754_log (x);
  return z + y * log10_2hi;
}
```

This is even worse: not only is there no native implementation, it's still branching, and there's no easy alternative to use in its place.

So I decided to write my own alternative. The first thing to consider is that counting the digits of an integer doesn't require us to deal with any floating point special cases or any of the other baggage that comes with IEEE 754. From this point on I shifted my focus to the more widely applicable `ilog10`, as you can easily convert that back to counting digits with a `+ 1`. So I started work on...

## My first version

My first version, which I came up with at the suggestion of a friend:

```c showLineNumbers run="ilog10(65537)"
long ilog10(long x)
{
    int n = -1;
    while (x != 0) {
        x /= 10;
        n++;
    }
    return n;
}
```

While this still contains looping, it is far less complicated than either of the two functions above, and serves as a clean method of understanding what it is we're trying to compute. The integer coarse logarithm base 10 is $\operatorname{ilog}_{10}(n) = y \iff 10^{y} \le n < 10^{y+1}$ or in simpler terms, the exponent of the largest power of ten that is at or below the number.

Inspired by the [fast inverse square root](https://en.wikipedia.org/wiki/Fast_inverse_square_root) I decided to search for bitwise hacks to help me make this implementation more efficient. After much googling, and eventually poring over the manual for GCC, I found [`__builtin_clzl`](https://gcc.gnu.org/onlinedocs/gcc/Bit-Operation-Builtins.html#index-_005f_005fbuiltin_005fclzl).

`__builtin_clzl`, or its 32-bit cousin `__builtin_clz`, is a GCC builtin function which takes an integer as its parameter and calculates the number of leading zeros in front of it. For example, were there an 8-bit version, the number of leading zeros returned by the function for `00001010` would be 4. The number of leading zeros is bounded by the datatype, e.g., the number of leading zeros for the number 1 would be 31 in a 32-bit datatype, and 63 in a 64-bit datatype, so on and so forth. On x86-64 this function becomes the opcode `bsr`, or, on supported architectures (Intel Haswell and later, AMD K10 and later), `lzcnt`[^2].

But you might be thinking, "How does this relate to calculating the ilog10 of a number?" Well, the astute among you may have already noticed you can take the length of the data type, subtract one, and then subtract the number of leading zeros, and get the logarithm base 2 of a number, i.e., `ilog2(x) = TYPE_LENGTH - 1 - __builtin_clz{l}{l}(x)`.

Subtracting one is necessary because bits are counted from 0: in our 8-bit example `00001010` has 4 leading zeros, and `8 - 4 = 4` is how many bits it takes to write 10, but its highest set bit is bit 3, and $2^3 = 8$ is the largest power of two not above 10, therefore $\operatorname{ilog}_2(10) = 3$.

At this point, however, I was stuck. While I had the log base 2 I didn't know where to go next. This led me down several rabbit holes[^3] until I remembered the logarithm change of base formula:
$$
\log_b x = \frac{\log_a x}{\log_a b}
$$
Which in our case we would substitute 2 and 10 in for $a$ and $b$ respectively:
$$
\log_{10} x = \frac{\log_2 x}{\log_2 10}
$$
Which we can then simplify, for our purposes, to:
$$
\log_{10} x = \log_2 x \cdot \frac{1}{\log_2 10} \approx \log_2 x \cdot \frac{1233}{4096}
$$
Meaning we can take our fast `ilog2(x)` and transform it into an `ilog10(x)` by multiplying it by the fraction $\frac{1233}{4096}$.

This, however, presents another problem as we have been dealing with integer types and the decimal version of $\frac{1233}{4096}$ is `0.301025390625` meaning floating point precision is required to perform this operation. Moving from floating point to integers and back is not ideal and claws back a lot of the gains we would have made doing this. However, there is a somewhat obvious way around this: by scaling up the constant (to the degree of precision we require[^4]), multiplying by it, and then dividing by the same scale factor, we can produce a very similar result but with integers. So something like $\operatorname{ilog}_2(x) \cdot 301025390625 / 10^{12}$.

However, this too presents a problem as, if you recall from earlier, I was trying to avoid doing division. This can be solved by choosing our scale a bit more carefully. Instead of scaling by a power of ten we can scale by a power of two, as dividing by a power of two is just a right shift. As luck would have it our decimal version of the constant reduces down perfectly, as $10^{12} = 2^{12} \cdot 5^{12}$ and $301025390625$ can be rewritten as $1233 \cdot 5^{12}$, meaning:

$$
\frac{301025390625}{10^{12}} = \frac{1233}{2^{12}}
$$

So our division by $10^{12}$ becomes a division by $2^{12}$, i.e., a right shift by 12, leaving us with `(ilog2(x) * 1233) >> 12`, no division required.

Our code so far would be something like this[^5]:

```c showLineNumbers run="ilog10(754)"
#include <limits.h>
#include <stdint.h>

#define LONGSIZE ((int)(sizeof(int64_t) * CHAR_BIT))

uint64_t ilog10(uint64_t x)
{
    uint64_t ilog2 = (LONGSIZE - 1) - __builtin_clzll(x);
    return (ilog2 * 1233) >> 12;
}
```

## Fixing the off-by-one

Sadly, this also has a problem, which is that this trick of doing `ilog10(x) = (ilog2(x) * 1233) >> 12` is not precise enough for all values of x. For example: if we take $x = 10$ then `ilog2(10) = 3`, and `(3 * 1233) >> 12` is `3699 >> 12`, which is `0`. However, `ilog10(10)` is of course `1`.

The issue here is one of precision. The trick we are using does not preserve the same level of precision as the slower $\log_2 x \cdot \frac{1233}{4096}$. This results in soft edges around values slightly above each power of ten, where the lack of precision prevents the correct amount of accumulation from happening, preventing the output from incrementing at the right time in the series; or more simply this trick sometimes has an off-by-one error.

Unfortunately there are no apparent methods of doing this operation, while maintaining (or improving)[^6] the performance characteristics of the trick, that achieve the level of accuracy needed. Meaning in order for the faster way of doing the operation to work we will need to apply some kind of correction factor.

And a correction factor we will add; the simplest way of doing so is to just check if we are above the nearest power of ten, and if so add one. But how will we know at what magnitude above the power of ten to stop applying the correction?[^7] Obviously once we get close to the next power of ten, but we stop needing the correction well before then, before we even hit the midway point between two powers of ten, and applying the correction past when it is needed would become an *in-correction*. Furthermore, how will we even find the closest power of ten?

The solution lies in the relationship between the number we are correcting and the nearest power of ten. Namely the number we are trying to correct, plus one, is the exponent of the power of ten that is the only one $x$ could be over and need correction. This is because at the exact number we would need to stop applying the correction, meaning our estimate has caught up, our estimate would increment and we would be comparing against the next power of ten which we would then be lower than.

The code for this looks like this:

```c showLineNumbers run="ilog10(15)"
#define _GNU_SOURCE
#include <limits.h>
#include <math.h>
#include <stdint.h>

#define LONGSIZE ((int)(sizeof(int64_t) * CHAR_BIT))

uint64_t ilog10(uint64_t x)
{
    uint64_t ilog2 = (LONGSIZE - 1) - __builtin_clzll(x);
    uint64_t estimate = (ilog2 * 1233) >> 12;
    return estimate + (x >= exp10(estimate + 1));
}
```

This is a big improvement and now should produce correct values, but we have introduced a new library call whose implementation we need to check, `exp10`:

```c title="[e_exp10.c](https://sourceware.org/git/?p=glibc.git;a=blob;f=sysdeps/ieee754/dbl-64/e_exp10.c)" dir="sysdeps/ieee754/dbl-64" showLineNumbers footer="[LGPL-2.1-or-later](/licenses/LGPL-2.1.txt)"
double
__exp10 (double x)
{
  uint64_t ix = asuint64 (x);
  uint32_t abstop = (ix >> 52) & 0x7ff;

  if (__glibc_unlikely (abstop - SmallTop >= Thresh))
    {
      if (abstop - SmallTop >= 0x80000000)
	/* Avoid spurious underflow for tiny x.
	   Note: 0 is common input.  */
	return x + 1;
      if (abstop == 0x7ff)
	return ix == asuint64 (-INFINITY) ? 0.0 : x + 1.0;
      if (x >= OFlowBound)
	return __math_oflow (0);
      if (x < UFlowBound)
	return __math_uflow (0);

      /* Large x is special-cased below.  */
      abstop = 0;
    }

  /* Reduce x: z = x * N / log10(2), k = round(z).  */
  double z = __exp_data.invlog10_2N * x;
  double kd;
  uint64_t ki;
#if TOINT_INTRINSICS
  kd = roundtoint (z);
  ki = converttoint (z);
#else
  kd = math_narrow_eval (z + Shift);
  ki = asuint64 (kd);
  kd -= Shift;
#endif

  /* r = x - k * log10(2), r in [-0.5, 0.5].  */
  double r = x;
  r = __exp_data.neglog10_2hiN * kd + r;
  r = __exp_data.neglog10_2loN * kd + r;

  /* exp10(x) = 2^(k/N) * 2^(r/N).
     Approximate the two components separately.  */

  /* s = 2^(k/N), using lookup table.  */
  uint64_t e = ki << (52 - EXP_TABLE_BITS);
  uint64_t i = (ki & IndexMask) * 2;
  uint64_t u = __exp_data.tab[i + 1];
  uint64_t sbits = u + e;

  double tail = asdouble (__exp_data.tab[i]);

  /* 2^(r/N) ~= 1 + r * Poly(r).  */
  double r2 = r * r;
  double p = C (0) + r * C (1);
  double y = C (2) + r * C (3);
  y = y + r2 * C (4);
  y = p + r2 * y;
  y = tail + y * r;

  if (__glibc_unlikely (abstop == 0))
    return special_case (sbits, y, ki);

  /* Assemble components:
     y  = 2^(r/N) * 2^(k/N)
       ~= (y + 1) * s.  */
  double s = asdouble (sbits);
  return s * y + s;
}
```

Unfortunately the implementation of this also presents us with some problems. Besides the fact that using this function requires us to convert into and back out of floating point, something we have gone to great lengths to avoid, it features branching and would end up taking most of the time in our function. Not only that but for large inputs it ends up being inaccurate, causing our function to be inaccurate too.

## Replacing exp10

Since the accuracy problem is a product of the limitations of floating point we must use an integer function to calculate our powers of ten. The tried-and-true method, and for good reason, is a lookup table. By making a static array and mapping the index to $10^i$ we can efficiently and accurately replace libc's `exp10`:

```c showLineNumbers run="ilog10(9999999999999999)"
#include <limits.h>
#include <stdint.h>

#define LONGSIZE ((int)(sizeof(int64_t) * CHAR_BIT))

static const uint64_t pow10[20] = { 1, 10, 100, 1000, 10000, 100000, 1000000, 10000000, 100000000, 1000000000, 10000000000, 100000000000, 1000000000000, 10000000000000, 100000000000000, 1000000000000000, 10000000000000000, 100000000000000000, 1000000000000000000, 10000000000000000000ULL };

uint64_t ilog10(uint64_t x)
{
    uint64_t ilog2 = (LONGSIZE - 1) - __builtin_clzll(x);
    uint64_t estimate = (ilog2 * 1233) >> 12;
    return estimate + (x >= pow10[estimate + 1]);
}
```

And after applying a few clean-ups and simplifications[^8] we arrive at:

```c showLineNumbers run="ilog10(42)"
#include <limits.h>
#include <stdint.h>

#define LONGSIZE ((int)(sizeof(int64_t) * CHAR_BIT))

static const uint64_t pow10[20] = { 1, 10, 100, 1000, 10000, 100000, 1000000, 10000000, 100000000, 1000000000, 10000000000, 100000000000, 1000000000000, 10000000000000, 100000000000000, 1000000000000000, 10000000000000000, 100000000000000000, 1000000000000000000, 10000000000000000000ULL };

uint64_t ilog10(uint64_t x)
{
    uint64_t estimate = ((LONGSIZE - __builtin_clzll(x)) * 1233) >> 12;
    return estimate - (pow10[estimate] > x);
}
```

## Stanford's version

At this point I was very happy: I had successfully reduced a series of expensive libc calls to just a couple of lines of simple math. However, despite having checked this at the beginning of this process and having somehow completely missed it, I soon learned that my solution was almost identical to the [Stanford Bit Twiddling Hacks](https://graphics.stanford.edu/~seander/bithacks.html) version:

```c title="[Find integer log base 10 of an integer](https://graphics.stanford.edu/~seander/bithacks.html#IntegerLog10)" dir="Bit Twiddling Hacks" showLineNumbers
unsigned int v; // non-zero 32-bit integer value to compute the log base 10 of 
int r;          // result goes here
int t;          // temporary

static unsigned int const PowersOf10[] = 
    {1, 10, 100, 1000, 10000, 100000,
     1000000, 10000000, 100000000, 1000000000};

t = (IntegerLogBase2(v) + 1) * 1233 >> 12; // (use a lg2 method from above)
r = t - (v < PowersOf10[t]);
```

And adding a similar method to find ilog2 as mine:

```c showLineNumbers
unsigned int IntegerLogBase2(unsigned int v)
{
    return 31 - __builtin_clz(v);
}
```

As you can see this version features all the same tricks as mine, minus using `__builtin_clz` for `ilog2`. While I was proud of myself for having come up with a near-identical solution to Stanford Bit Hacks, I found it unfortunate that pretty much all of my work had already been done previously. Not discouraged, I decided I was going to, somehow, make this already ridiculously simple function faster. To do that I turned to the x86 assembly my function produces:

```asm title="ilog10" dir="gcc 16.2.1 -O2 -march=x86-64-v3" showLineNumbers run="rdi=1233"
xor     edx, edx
mov     eax, 64
lzcnt   rdx, rdi
sub     eax, edx
imul    eax, eax, 1233
sar     eax, 12
cmp     rdi, QWORD PTR pow10[0+rax*8]
sbb     rax, 0
ret
```

This assembly is excellent, only eight instructions[^9] and almost a direct translation of each operation into assembly:

| C | Assembly | Line |
| --- | --- | --- |
| `__builtin_clzll(x)` | `xor edx, edx`<br/>`lzcnt rdx, rdi` | 1, 3 |
| `LONGSIZE - …` | `mov eax, 64`<br/>`sub eax, edx` | 2, 4 |
| `… * 1233` | `imul eax, eax, 1233` | 5 |
| `… >> 12` | `sar eax, 12` | 6 |
| `pow10[estimate] > x` | `cmp rdi, QWORD PTR pow10[0+rax*8]` | 7 |
| `estimate - (…)` | `sbb rax, 0` | 8 |
| `return` | `ret` | 9 |

However, two of the operations compile into two instructions. The first is `__builtin_clzll(x)`, which gets an extra `xor` because of how some x86 CPUs implement `lzcnt`[^10]; the important thing to know is that on most CPUs this instruction is effectively free.

The other is more troubling: when converting from the count of leading zeros to the bit length, a simple subtraction, `LONGSIZE - …`, produces both a `mov` and a `sub` instruction. This is because, on x86, most two-operand instructions can only take a constant value in the second operand, meaning if you are trying to operate on a constant you must put it second.

This presents no problem for something like `add` which is commutative, as you can simply swap your constant and your register and produce the same result. With something non-commutative, like `sub`, however, this presents us with a problem as swapping the parameters will produce a different result, e.g., $x - y \neq y - x$.

The solution to this is to move your constant into a register. But this is not ideal, as now not only do you have to execute a non-required[^11] `mov` instruction, by moving your constant into a register, you are now potentially taking up a register that could have been used for something else. This matters far more in the context of inlining, the ideal case for this function, as from the perspective of writing this function you have no idea what the implications of taking up an additional register are, and thus for best performance must assume the worst.

## Getting rid of the mov

But how would we fix this? For a time this stumped me. I thought it was simply impossible to improve this function any further, until one day when playing around with different compilers in [Godbolt](https://godbolt.org/), I noticed Clang applied a peculiar transformation to the assembly of a previous version of the function[^12]:

```asm title="ilog10" dir="clang 22.1.8 -O2 -march=x86-64-v3" showLineNumbers run="rdi=418"
lzcnt   rax, rdi
xor     eax, 63
imul    eax, eax, 1233
shr     eax, 12
cmp     rdi, qword ptr [8*rax + pow10+8]
sbb     rax, -1
ret
```

Instead of a `mov` and a `sub`, `(LONGSIZE - 1) - __builtin_clzll(x)` became a single `xor eax, 63`, which was very strange to me. How did this even work and how was it possible that it produced the same results?

The answer lies in the binary. The count of leading zeros is always between 0 and 63, and 63 is `111111` in binary, all ones. Subtracting a number in that range from all ones never needs to borrow, so each bit of the result is just the opposite of the same bit in the number being subtracted, i.e., a `xor` with 63 produces the same result as subtracting from 63. Take 418, which has 55 leading zeros: $63 - 55 = 8$, and `110111` `xor` `111111` is `001000`, also 8.[^13]

This is awesome as it completely eliminates the need for a `mov`, as `xor` is commutative so we can simply swap around the parameters! Unfortunately this too presents a problem; this only works because the previous version subtracts from 63. Our current version subtracts from 64, the bit length, and 64 is `1000000` in binary, not all ones, so no single `xor` can replace the `sub`.

We also can't simply go back to the previous version: `__builtin_clzll(0)` is undefined in C, but on x86 the `lzcnt` instruction returns 64 for it, and $64 \oplus 63 = 127$, which makes the estimate 38. The table lookup then reads entry 39 (counting from 0) of our 20-entry table, well past its end, reading whatever memory happens to come after it. Our current version has no such issue: for 0 the bit length is 0, and the lookup stays at the first entry.

But the same kind of trick still works if we come at it from the other side. Instead of $64 - n$ we can compute $n - 64$. Since $n$ is always below 64, all of its bits above the sixth are zero, and $-64$ in two's complement is exactly those bits set: `…11000000`. So an `or` of $n$ with $-64$ never has to carry, and gives $n - 64$ in a single instruction.

That is the negative of the bit length we want, but the negative sign can easily be inverted: we are about to multiply by $1233$ anyway, so multiplying by $-1233$ instead inverts it and gives us the correct output:

```c showLineNumbers run="ilog10(0)"
#include <limits.h>
#include <stdint.h>

#define LONGSIZE ((int)(sizeof(int64_t) * CHAR_BIT))

static const uint64_t pow10[20] = { 1, 10, 100, 1000, 10000, 100000, 1000000, 10000000, 100000000, 1000000000, 10000000000, 100000000000, 1000000000000, 10000000000000, 100000000000000, 1000000000000000, 10000000000000000, 100000000000000000, 1000000000000000000, 10000000000000000000ULL };

uint64_t ilog10(uint64_t x)
{
    uint64_t estimate = ((__builtin_clzll(x) | (-LONGSIZE)) * -1233) >> 12;
    return estimate - (pow10[estimate] > x);
}
```

For 0, `lzcnt` gives 64, and $64 \mathbin{|} -64 = -64$, which the multiply and shift turn into 19, the last entry in the table, so even an input of 0 never reads out of bounds on the array.

The assembly for this function is beautiful:

```asm title="ilog10" dir="gcc 16.2.1 -O2 -march=x86-64-v3" showLineNumbers run="rdi=1597463007"
xor     eax, eax
lzcnt   rax, rdi
or      eax, -64
imul    eax, eax, -1233
sar     eax, 12
cmp     rdi, QWORD PTR pow10[0+rax*8]
sbb     rax, 0
ret
```

A whole seven instructions, or six if your compiler isn't padding `lzcnt` with a `xor`[^10].

## Seven instructions

Seven instructions seemed like the end of the road, but the `imul` kept bugging me. A multiply takes three cycles, and everything after has to wait for it to finish. When I thought about it more, I realized the only reason $\frac{1233}{4096}$ is there is because it's a very good approximation of $\log_{10}(2)$, but we don't actually need a very good approximation. We only need an estimate that's never too low and never more than one too high, since the comparison against the table gives us the rest of the precision.

So I started looking for the cheapest multiply and shift that still has enough precision. The OR trick already gives us `lz - 64`, which is the bit length as a negative number, so what if we multiply that by 5 and shift right by 4? That's multiplying by $\frac{5}{16} = 0.3125$, a worse guess at $\log_{10}(2) \approx 0.30103$ than before, but it's still within one of the right answer for every possible number of leading zeros, and since there are only 65 of those it's easy to check them all.

Something nice then happens with the math. $(5 \cdot \mathit{lz} - 320) \gg 4$ is exactly $((5 \cdot \mathit{lz}) \gg 4) - 20$, because $320 = 20 \cdot 16$, so the $-64$ folds right out of the shift and we don't need the OR at all anymore. If we store the powers of ten in reverse, $e = (5 \cdot \mathit{lz}) \gg 4$ can index them directly and the estimate is just $19 - e$. Even better, multiplying by 5 doesn't need a multiply on x86, as `lea` can add a register to four times itself in a single instruction, i.e., $5x = x + 4x$.

This makes our code:

```c showLineNumbers run="ilog10(4096)"
#include <stdbit.h>
#include <stdint.h>

static const uint64_t pow10_rev[21] = { 10000000000000000000ULL, 1000000000000000000, 100000000000000000, 10000000000000000, 1000000000000000, 100000000000000, 10000000000000, 1000000000000, 100000000000, 10000000000, 1000000000, 100000000, 10000000, 1000000, 100000, 10000, 1000, 100, 10, 1, 0 };

uint64_t ilog10(uint64_t x)
{
    uint64_t e = (stdc_leading_zeros(x) * 5) >> 4;
    return (19 - e) - (x < pow10_rev[e]);
}
```

This version also has two other small changes. `stdc_leading_zeros` is C23's standard version of `__builtin_clzll`, and unlike the builtin it's defined for 0, where it returns the width of the type, which means `ilog10(0)` is now actually defined instead of relying on `lzcnt` returning 64, which may not be true on all architectures. It still gets compiled down to a single `lzcnt` on x86-64-v3.

The table also needed a 21st entry, a 0, which is what keeps a zero input from accessing the array out of bounds. For 0 `lzcnt` gives 64, so $e = 20$, $0 < 0$ is false, and we return $19 - 20 = -1$, which I think is a more sensible answer for the log of 0 than the 18 the old version gave.

```asm title="ilog10" dir="gcc 16.2.1 -O2 -march=x86-64-v3" showLineNumbers run="rdi=0"
xor     eax, eax
lzcnt   rax, rdi
lea     rdx, [rax+rax*4]
mov     eax, 19
shr     rdx, 4
sub     rax, rdx
cmp     rdi, QWORD PTR pow10_rev[0+rdx*8]
sbb     rax, 0
ret
```

## Why the longer version is faster

If you've been counting you'll notice this version is actually one instruction longer than before, eight up from seven. Instruction count turns out not to be the whole story, because a modern CPU doesn't run instructions one at a time. If an instruction doesn't need the result of the one before it, the CPU can start it without waiting for the previous one to finish, called out-of-order execution. What actually decides how long you wait for the answer is the longest run of instructions where each one has to wait for the one before it to finish, called the critical path. ## Lemire's version

If you've ever tried to do micro-optimization work like this you've probably come across Daniel Lemire. He's a professor who makes similar posts, and one of the people behind simdjson and fast_float. In January 2025 he wrote [Counting the digits of 64-bit integers](https://lemire.me/blog/2025/01/07/counting-the-digits-of-64-bit-integers/), and one of the versions in it is the fastest I've seen anyone come up with. It counts the number of digits (what originally led me down this path), rather than taking the log, but just like mine his can easily be converted between counting digits and `ilog10`.

```cpp title="[alternative_digit_count_two_tables](https://lemire.me/blog/2025/01/07/counting-the-digits-of-64-bit-integers/)" showLineNumbers
int alternative_digit_count_two_tables(uint64_t x) {
  static int digits[65] = {19, 19, 19, 19, 18, 18, 18, 17, 17, 17, 16, 16, 16, 16, 15, 15, 15, 14, 14, 14, 13, 13, 13, 13, 12, 12, 12, 11, 11, 11, 10, 10, 10, 10, 9, 9, 9, 8, 8, 8, 7, 7, 7, 7, 6, 6, 6, 5, 5, 5, 4, 4, 4, 4, 3, 3, 3, 2, 2, 2, 1, 1, 1, 1, 1};
  static uint64_t table[65] = {18446744073709551615ULL, 18446744073709551615ULL, 18446744073709551615ULL, 18446744073709551615ULL, 999999999999999999ULL, 999999999999999999ULL, 999999999999999999ULL, 99999999999999999ULL, 99999999999999999ULL, 99999999999999999ULL, 9999999999999999ULL, 9999999999999999ULL, 9999999999999999ULL, 9999999999999999ULL, 999999999999999ULL, 999999999999999ULL, 999999999999999ULL, 99999999999999ULL, 99999999999999ULL, 99999999999999ULL, 9999999999999ULL, 9999999999999ULL, 9999999999999ULL, 9999999999999ULL, 999999999999ULL, 999999999999ULL, 999999999999ULL, 99999999999ULL, 99999999999ULL, 99999999999ULL, 9999999999ULL, 9999999999ULL, 9999999999ULL, 9999999999ULL, 999999999ULL, 999999999ULL, 999999999ULL, 99999999ULL, 99999999ULL, 99999999ULL, 9999999ULL, 9999999ULL, 9999999ULL, 9999999ULL, 999999ULL, 999999ULL, 999999ULL, 99999ULL, 99999ULL, 99999ULL, 9999ULL, 9999ULL, 9999ULL, 9999ULL, 999ULL, 999ULL, 999ULL, 99ULL, 99ULL, 99ULL, 9ULL, 9ULL, 9ULL, 9ULL, 0ULL};
  int log = std::countl_zero(x);
  uint64_t low = table[log];
  uint64_t high = digits[log];
  return (x > low) + high;
}
```

His idea is to not calculate anything at all. The leading zero count goes straight into two different tables. `digits[lz]` is how many digits the smallest number with that many leading zeros has, and `table[lz]` is the largest number with that many digits, $10^d - 1$[^15], so `x > table[lz]` means x has one more digit, and that comparison is the entire correction. Since both tables are indexed by the leading zero count itself, the CPU can start both loads as soon as `lzcnt` finishes.

```asm title="digit_count" dir="g++ 16.2.1 -std=c++20 -O2 -march=x86-64-v3" showLineNumbers
xor     eax, eax
lzcnt   rax, rdi
cmp     QWORD PTR table[0+rax*8], rdi
mov     eax, DWORD PTR digits[0+rax*4]
adc     eax, 0
ret
```

Natively, his beats my folded version on every machine I tried. Compare what the first table load has to wait for in each. In his it only waits for `lzcnt`, while in mine it waits for `lzcnt`, then `lea`, then `shr`, which is two extra steps on the critical path on every call.

## Combining the two

Looking at the two next to each other, the obvious question was whether I could take the best half of each. His table load starts right away, but he needs a second table to get the answer. My estimate doesn't need a table at all, but my table load has to wait for it. So what if the table were indexed by the leading zero count like his, and the answer came from my fold?

```c showLineNumbers run="ilog10(1729)"
#include <stdbit.h>
#include <stdint.h>

static const uint64_t pow10_lz[65] = { 10000000000000000000ULL, 10000000000000000000ULL, 10000000000000000000ULL, 10000000000000000000ULL, 1000000000000000000, 1000000000000000000, 1000000000000000000, 100000000000000000, 100000000000000000, 100000000000000000, 10000000000000000, 10000000000000000, 10000000000000000, 1000000000000000, 1000000000000000, 1000000000000000, 100000000000000, 100000000000000, 100000000000000, 100000000000000, 10000000000000, 10000000000000, 10000000000000, 1000000000000, 1000000000000, 1000000000000, 100000000000, 100000000000, 100000000000, 10000000000, 10000000000, 10000000000, 1000000000, 1000000000, 1000000000, 1000000000, 100000000, 100000000, 100000000, 10000000, 10000000, 10000000, 1000000, 1000000, 1000000, 100000, 100000, 100000, 10000, 10000, 10000, 10000, 1000, 1000, 1000, 100, 100, 100, 10, 10, 10, 1, 1, 1, 0 };

uint64_t ilog10(uint64_t x)
{
    uint64_t lz = stdc_leading_zeros(x);
    uint64_t e = (lz * 5) >> 4;
    return (19 - e) - (x < pow10_lz[lz]);
}
```

```asm title="ilog10" dir="gcc 16.2.1 -O2 -march=x86-64-v3" showLineNumbers run="rdi=8086"
xor     edx, edx
mov     eax, 19
lzcnt   rdx, rdi
lea     rcx, [rdx+rdx*4]
shr     rcx, 4
sub     rax, rcx
cmp     rdi, QWORD PTR pow10_lz[0+rdx*8]
sbb     rax, 0
ret
```

The important line in the assembly is 7. The table load there only needs `rdx`, which `lzcnt` produced on line 3, so it can start straight away. Meanwhile lines 4 to 6 work out $19 - e$ from the same `rdx`, so by the time the load comes back that's ready too, and the `sbb` on line 8 finishes off with both. That makes the critical path `lzcnt`, the load and compare, then `sbb`, which is as short as Lemire's. The difference is that mine makes one table load instead of two, from a single 520-byte table, while his two tables total 780 bytes as published.

## Where Lemire's is still faster

Lowest latency isn't the same thing as fastest, though, and thus there are two places where Lemire's still wins.

The first is throughput. When the calls don't depend on each other, like a loop adding up the digit counts of a whole array, the CPU works on several at once, and what matters is how much work each call costs in total, not how long one takes from start to finish. His compiles to five instructions to my eight, and takes 21 to 33 percent less time per call[^14].

The second is Arm, where his is as fast or faster even for a single call. Here are both on a Raspberry Pi 5, starting with Lemire's as G++ compiles it:

```arm64 title="digit_count" dir="g++ 14.2.0 -O2 -mcpu=cortex-a76" showLineNumbers run="x0=2001"
adrp    x1, table
clz     x3, x0
add     x2, x1, :lo12:table
adrp    x1, digits
ldr     x2, [x2, w3, sxtw 3]
add     x1, x1, :lo12:digits
ldr     w1, [x1, w3, sxtw 2]
cmp     x0, x2
cinc    w0, w1, hi
ret
```

And mine:

```arm64 title="ilog10" dir="gcc 14.2.0 -O2 -mcpu=cortex-a76" showLineNumbers run="x0=2001"
adrp    x1, pow10_lz
clz     x3, x0
add     x2, x1, :lo12:pow10_lz
add     x1, x3, x3, lsl 2
ldr     x2, [x2, w3, sxtw 3]
mov     x3, 19
sub     x1, x3, x1, lsr 4
cmp     x2, x0
cset    x0, hi
sub     x0, x1, x0
ret
```

Both start their table loads as soon as `clz` is done, but after the compare his only needs a `cinc`, which adds one if the condition holds, while GCC ends mine with a `cset` and then a `sub`. Arm does have a subtract with borrow, `sbc`, that could do both at once like `sbb` does on x86, but GCC doesn't use it here, and that one extra step after the compare is enough for his to come out ahead on Arm.

Which one is faster for you depends on what you are doing with the answer. If your program needs it before it can perform its next task, low latency is what you want, which is where my function wins. That often covers formatting a number, since you need to know how many digits it has before you can start writing them from the end; writing numbers one after another, like the integers in a JSON array, where each one starts where the last one ended; allocating a string of exactly the right size, like Java's `Long.toString`; padding a single number to a fixed width, where you need its length to know how many spaces go before it; and any one-off call with nothing else for the CPU to overlap it with.

If you're working through lots of numbers whose answers don't depend on each other, use Lemire's. That covers adding up how much space a whole array of numbers will take as text, so you can allocate one buffer for all of them; finding the widest number in a column, to know how wide to make it; counting how many numbers have each length, for a histogram or to sort them into buckets by size; and any loop where the CPU can start on the next number before it's finished with the last.

## So is this the fastest ilog10?

So is this the fastest ilog10? It started as my own take on what turned out to be in Stanford Bit Hacks, became my seven-instruction OR trick, then the fold, which was 12 to 17 percent faster again, and finally the hybrid, which borrows Lemire's table indexing and replaces his second table with my fold. On x86, for a single call, it's the fastest I've found with every compiler and browser engine I tried. For big batches, 32-bit integers[^18], or on Arm, Lemire's is still the one to beat, but he's in Montreal and I'm west in Denver, so I'll settle for being the fastest in the West 🤠.
